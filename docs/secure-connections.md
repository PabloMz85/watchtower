Watchtower is also capable of connecting to Docker endpoints which are protected by SSL/TLS. If you've used _docker-machine_ to provision your remote Docker host, you simply need to volume mount the certificates generated by _docker-machine_ into the watchtower container and optionally specify `--tlsverify` flag.

The _docker-machine_ certificates for a particular host can be located by executing the `docker-machine env` command for the desired host (note the values for the `DOCKER_HOST` and `DOCKER_CERT_PATH` environment variables that are returned from this command). The directory containing the certificates for the remote host needs to be mounted into the watchtower container at _/etc/ssl/docker_.

With the certificates mounted into the watchtower container you need to specify the `--tlsverify` flag to enable verification of the certificate:

```bash
docker run -d \
  --name watchtower \
  -e DOCKER_HOST=$DOCKER_HOST \
  -e DOCKER_CERT_PATH=/etc/ssl/docker \
  -v $DOCKER_CERT_PATH:/etc/ssl/docker \
  pablomz85/watchtower --tlsverify
```

## Registry HTTPS and token cache

Registry authentication and manifest HEAD checks use a separate instance-owned HTTPS client, not the Docker API transport above. Certificate chains and hostnames are verified by default for challenge, token **and** HEAD requests. For a private registry or token service CA, mount a PEM bundle read-only and pass `--registry-ca=/run/certs/registry-ca.pem` (or `WATCHTOWER_REGISTRY_CA`). The bundle adds to system roots, is strictly parsed once at startup, and must contain only valid CA certificate PEM blocks. Empty, unreadable, oversized or partly invalid bundles abort startup. Restart Watchtower after rotating this file. There is no registry insecure-TLS flag.

Docker daemon pulls use the daemon's own registry CA configuration (typically its `certs.d` directory); `--registry-ca` does **not** configure the daemon, nor does `--tlsverify` configure registry trust. A failed HEAD check still falls back to the existing daemon pull path. Configure both trust domains when needed.

Only absolute HTTPS endpoints without userinfo or fragments are accepted. Redirects are bounded and may not leave the original host/port or downgrade to HTTP. Legitimate registries redirecting their token endpoint to another origin must instead advertise the final HTTPS realm in their challenge. Requests have a 30-second default timeout, bounded response headers and a 1 MiB challenge/token body limit. Errors omit raw response bodies, authentication headers, credentials and sensitive endpoint URLs.

### Instance-scoped token cache

Each application Docker client receives one registry auth/digest client. It reuses bearer tokens (and avoids repeating the challenge while that token is fresh). The default RAM backend is a concurrent 1024-entry LRU with lazy expiry and no refresh goroutines or disk writes. Route metadata is separately bounded to 1024 entries. Cache identity covers the exact realm, service, computed repository pull scope, registry and credential value/version, including anonymous access as a separate identity. Keys are per-instance HMAC-SHA256 values using a cryptographically random key; plaintext credentials are not stored in keys. Entries carry a key/token/expiry HMAC and are checked again on every backend read.

Omitted `expires_in` uses 60 seconds. Explicit lifetimes must be positive integer seconds no greater than 24 hours. `issued_at`, when present, must be a valid RFC3339 timestamp not in the future. Five seconds are subtracted as a safety margin; already-expired tokens and lifetimes within that margin are rejected, never cached indefinitely. Rejected manifest authentication (401/403) invalidates the corresponding token so the next attempt refreshes it; it does not automatically retry the failed HEAD. A late rejection cannot evict a newer token. Cache failures fail the HEAD/auth optimization closed and preserve the normal Docker pull fallback. If deletion of a rejected token fails, that auth client refuses further cache/auth reuse until replaced or restarted.

For library use, `auth.NewClient(auth.ClientOptions{Clock: instanceClock, Cache: backend})` accepts `pkg/clock.Clock` and `auth.TokenCache` (`Get`, `Set`, `Delete`), and `digest.NewClient` shares the provider for HEAD. Nil options select `clock.RealClock` and the bounded RAM default; typed-nil options are errors. Inject the digest client via `container.ClientOptions.Registry`. Compatibility functions `auth.GetToken`, `auth.GetBearerHeader`, `digest.GetDigest` and `digest.CompareDigest` retain their signatures but create fresh secure clients, so reusable caching requires the instance APIs. Concurrent misses are coalesced by a context-cancellable per-client gate; slow misses serialize and waiters may cancel. No background refresh or unbounded in-flight maps are created.

No Redis, Memcache, file cache, backend dependencies or cache infrastructure settings are included. External backends are deferred. A future shared backend must explicitly design cross-instance key/signature coordination and storage confidentiality; the current random per-instance HMAC identity intentionally prevents cross-instance cache sharing. Do not replace it with an unkeyed credential hash or expose the process key as an ad-hoc environment setting.
